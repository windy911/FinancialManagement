# Git 规范

## 1. 分支规范

### 1.1 基本原则

- 禁止本地直接改 master 分支代码，必须在独立的任务分支上修改代码
- 默认从 master 分支创建新开发分支，创建之前先 pull master 分支最新版本，保持与 master 分支同步

### 1.2 分支命名

| 类型 | 命名格式 | 用途 |
|------|---------|------|
| feature | `feature/<变更名>-m-<飞书任务id>` | 新功能开发 |
| bugfix | `bugfix/<变更名>-f-<bug id>` | Bug 修复 |
| hotfix | `hotfix/<变更名>-f-<bug id>` | 生产环境紧急修复 |

- 变更名使用英文小写 + 连字符，如 `update-sdd`、`fix-login-error`
- 可以根据对话内容自动识别变更名和飞书任务 id/bug id，自动生成分支名，询问用户确认后创建分支
- 对话内容中如果没有明确的飞书任务 id 或 bug id，询问用户是否需要关联飞书任务 id 或 bug id
  - 如果需要关联，要求用户提供飞书任务 id 或 bug id，并根据提供的信息生成分支名
  - 如果用户确认不需要关联，允许创建不包含任务 id 的分支，格式为 `feature/<变更名>` 或 `bugfix/<变更名>`，但必须在对话中记录用户确认过程

### 1.3 当前分支校验

- 如果当前分支名包含飞书任务 id 或 bug id，且与当前 task/fix 相关，允许在当前分支上修改代码
- 否则禁止在当前分支上修改代码，必须切换到 master 分支并从 master 分支最新版本创建新分支
- 若当前已处于非规范命名的分支且存在未提交改动，询问用户「继续当前分支」还是「迁出到新规范分支」

## 2. Commit 规范

### 2.1 提交时机

- 每个 task/fix 禁止自动 commit，准备好 commit 之后向用户确认  <!--备注：开发者熟悉流程之后可以改为自动commit，无需用户确认-->
- 仅 commit 与当前 task/fix 相关的变更，禁止 commit 与当前 task/fix 无关的变更
- Commit 必须可编译

### 2.2 Message 格式

```
[<变更名>] <中文简述> <任务id>
```

- 示例：`[年龄门控] 修复校验逻辑 m-6928766508`
- 变更名与分支名中的变更名保持一致
- 简述控制在 50 字以内，清晰说明做了什么（而非怎么做）
- 任务 id 格式：`m-<飞书任务id>` 或 `f-<bug id>`
- Message 中禁止附带 "Co-Authored-By: AI" 等 AI 相关标识，保持 commit 纯净

### 2.3 任务 ID 要求

- 分支和 commit **原则上**必须包含对应的飞书任务 id 或 bug id
- 如用户确认不关联任务，commit message 中可省略任务 id，但需在对话中记录确认过程

---

## 3. Push 与合并规范

- 禁止自动 push，准备好 push 之后向用户确认
<!--推送前确保本地分支已通过 `rebase master` 保持最新-->
- 合并分支必须通过 gitlab PR/MR，禁止直接 push 到 master
